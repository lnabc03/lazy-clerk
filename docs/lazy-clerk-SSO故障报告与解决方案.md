# lazy-clerk 医院 SSO 连接故障排查报告与解决方案

> 生成日期：2026-09-12
> 服务器：阿里云 ECS（深圳），公网出口 IP `8.135.34.161`
> 目标系统：`my.gzsums.net:1118`（统一登录 SSO）/ `:1198`（实习考勤），解析 `14.23.155.10`（广东电信）

---

## 1. 故障现象

- 服务部署后稳定运行一天：`09-11` 晚间上线，`09-12` 上午 6:58、下午 13:58 两批签到（每批 7-8 人）**全部成功**。
- `09-12` 晚间起，SSO 验证**无法连接**，报错为 `ConnectTimeout`（连接超时）。
- 应用本身（`127.0.0.1:8787`）正常，仅"访问医院平台"这一外部链路失效。

## 2. 排查过程与证据

| 检查项 | 结果 | 说明 |
|---|---|---|
| 容器内直连 `my.gzsums.net:1118/1198` | ❌ `ConnectTimeout` | 部署当天为 `200`，现已不通 |
| 宿主机 TCP 全端口（1118/1198/80/443/22） | ❌ 全部超时 | 非单端口问题，是整机 TCP 被丢 |
| `ping 14.23.155.10` | ✅ 3/3 通，约 7.5ms | 目标主机在线、路由正常 |
| `curl -v http://14.23.155.10:80/` | ❌ `Connection timed out`（非 `refused`） | **SYN 被静默丢弃**；若仅端口关闭会回 RST |
| DNS 解析 | `my.gzsums.net → 14.23.155.10` | 解析正常 |
| 本机出口 IP | `8.135.34.161`（阿里云 深圳） | 与需求方所述一致 |
| 日志时间线 | 13:58 那批全部成功 → 19:11 手动签到开始失败 | 封禁发生在当天下午之后 |

**对照组**（由需求方提供，用于排除系统侧问题）：

- 医院系统正常：企微（企业微信）正常渠道可进入。
- 医院密钥未轮换：本地运行 dev 版（不同源 IP）可正常连接。

## 3. 根因判定

**目标侧（医院网络防火墙 / SSO 风控）把本服务器公网 IP `8.135.34.161` 的 TCP 流量拉黑了。**

判定依据（特征完整闭环）：

1. 目标主机在线（`ping` 通）、路由正常（tracepath 可达 `14.23.155.1`）；
2. 但来自 `8.135.34.161` 的**所有 TCP 端口**请求均被**静默丢弃**（超时而非拒绝）；
3. 同一目标、不同源 IP（本地 dev）可正常连接 → 排除"医院系统挂了 / 密钥轮换"。

这是"源 IP 被防火墙/WAF 针对性地 drop TCP、同时放行 ICMP"的典型特征。

## 4. 触发机制分析

一个重要细节：封禁**并非在 13:58 那批请求的当场触发**（那批全成功），而是下午到晚上之间才生效。这更像**延迟 / 人工的风控封禁**（安全侧看到"同一 IP 短时间登录了 7-8 个不同账号"的日志后手动拉黑），而非即时限流。

根因的本质行为特征是：**"一个源 IP 代理多人登录"**，天然命中 SSO 的撞库 / 批量登录风控规则。

> 推论：这类封禁**不保证 24h 自动过期**（人工拉黑可能持久），且即使换一个阿里云 IP，只要仍保持"单 IP 多账号"模式，仍有再次被封的风险。

## 5. 解决方案评估

### 5.1 医院信息科加白名单（治本，但不可行）

需求方明确表示**信息科白名单拿不到**，此路径排除。

### 5.2 等待自动解封（零成本）

观察 24-48h 是否自动恢复。明早 6:58 那批签到是天然探针。优点零成本；缺点不确定、易复发。

### 5.3 多出口 IP（轻量服务器 / 家宽代理池）

| 子方案 | 成本 | 说明 |
|---|---|---|
| 单买 EIP | 约 124 元/年/个 | 需求方认为偏贵 |
| **轻量应用服务器当代理节点** | 促销年付几十元/台（含公网 IP + 小机器） | 比单买 EIP 更划算，还能直接跑 forward proxy |
| 家宽/办公宽带盒子 | ≈0（旧电脑/树莓派 + 现有宽带） | 出口是**天然正常用户 IP**，最稳 |

关键设计：**per-account 固定出口**（每个账号固定走一个 IP），彻底消除"单 IP 多账号"特征，且某 IP 被封只影响绑定它的账号。

### 5.4 云函数 Serverless 转发（重点调研，见第 6 节）

### 5.5 商业 HTTP 代理（按量/按次）

不推荐。机房代理 IP 异地、本身易被标记；动态住宅代理较贵、慢、借用真实用户 IP。用在安全敏感的医院 SSO 上大概率更糟。

## 6. 云函数（阿里云 FC）调研详情

### 6.1 能否做到"每段请求 IP 不同"？——**不能（关键结论）**

这是需求方最关心的问题，答案明确：

- FC 默认出口 IP 是**动态、无固定网段、不可枚举**的；
- 但变化粒度是**实例**，不是**请求**：同一热实例被复用时，出口 IP **相同**；
- 实例空闲约 **3-15 分钟**（常见口径 3-5 分钟，可配"弹性实例延迟释放"至最长 60 分钟）后被回收，下次**冷启动**才可能拿到新 IP；
- **没有机制强制"每次调用 / 每段签到换一个 IP"**。

结论：FC **不能**提供"每账号不同 IP"或"可控轮换多 IP"。它只能做到"换一个不再是 `8.135.34.161` 的新机房 IP，且被回收后偶尔会变"。

### 6.2 要固定 IP 反而更贵

若想让 FC 出网 IP 固定，需 `VPC + NAT 网关 + EIP`：

- NAT 网关按量约 **0.23 元/小时**（约 5.5 元/天、165 元/月），另加 EIP 费用；
- 成本**远高于单买 EIP（124 元/年）**，失去了"几乎免费"的意义。

### 6.3 端口限制：支持任意端口（1118/1198 可用）

- 官方文档未显示 FC 出网访问有"仅 80/443"的限制；80/443 限制仅出现在**入方向**（网关回源到函数）场景。
- FC 本质是容器发起出站连接，可访问非标准端口。稳妥起见可提交工单二次确认。

### 6.4 计费：免费额度内基本 0 成本

- FC 采用 CU 计费；新用户免费额度约 **每月 100 万次调用 + 40 万 CU·秒资源**。
- 本项目每天仅 ~15 条签到链路（几十次调用），远在免费额度内，实际开销≈0。
- 公网出流量按 CDT 另计，量极小。

### 6.5 FC 的定位小结

| 维度 | 结论 |
|---|---|
| 按次计费、代发请求 | ✅ 满足，成本≈0 |
| 换掉被封的 `8.135.34.161` | ✅ 满足（新阿里云池 IP） |
| 支持任意端口 1118/1198 | ✅ 满足 |
| **每段请求 IP 不同** | ❌ 不满足（实例级动态，不可控） |
| 可控多 IP / 固定 IP | ❌ 需 NAT+EIP，成本反超 |

**结论：FC 适合作为"换一个新源 IP、按次计费、几乎免费"的应急/过渡方案，但它不是"IP 池"——不能满足"每账号固定不同 IP / 可控轮换"这一核心诉求。**

## 7. 综合推荐路径

按优先级：

1. **立即联系医院信息科申请白名单**——已明确拿不到，跳过，但仍建议保留书面诉求作为备查。
2. **先试云函数 FC 转发（≈0 成本、按次计费、能连任意端口）**：换一个不再是 `8.135.34.161` 的源 IP，若医院风控是"针对该 IP"而非"针对阿里云网段"，即可立即恢复。
3. **若 FC 也很快被封（说明是"机房 IP + 多账号"组合特征被拦）**：转 **轻量服务器代理池 / 家宽盒子**，做 per-account 固定出口，用"正常用户 IP"根治。

## 8. 落地形态（供后续实施）

### 8.1 云函数 FC 版（方案 2）

把 `HospitalClient` 整条链路（login → 拉考勤 → 判定 → 提交）封装为函数 `do_sign(account, password)`：

- 函数内部用**同一个 httpx client** 走完链路，保证整条链路同一出口 IP、同一会话；
- 主服务 `signer` 改为调用该函数（HTTP 触发或 SDK 直调）；
- 函数部署在**广州/深圳地域**，保证地理上仍为广东。

改动范围：`client.py` / `signer.py` 抽离出可部署到 FC 的 handler，新增 FC 部署配置。

### 8.2 per-account 代理池版（方案 3）

- `User` 表加 `proxy` 字段，`HospitalClient` 加 `proxy=` 参数；
- 代理节点：轻量服务器跑 tinyproxy/3proxy，主服务经 WireGuard 内网连代理（不暴露开放代理）；
- `signer` 按 `user.proxy` 建 client，账号固定出口。
