# 代理逃生通道（mihomo）已知问题与架构决策

> 记录公网版代理逃生通道（mihomo sidecar）的架构决策与已修复问题。
> 当前架构：**app 钉节点 + 双通道探针是出口决策的唯一大脑**，mihomo 只执行。
> （试错期的 v0.3.x/v0.4.0 版本号已收回，统一发布为 v0.2.0。）

## 当前架构（2026-09-17 定稿）

- `hospital` 组为 **selector**（`DIRECT` / `hospital-pin`），不自主切换——
  出口选择由 app 探针按双通道实测决定（见 `app/core/client.py probe()`）。
- `hospital-pin` 为 **select**（订阅全节点）：app 按医院首页实测钉住一个节点，
  好节点一直用，实测失败才全量重测换节点。url-test 自动选速已废弃——
  每 5 分钟单样本重选 = 每 5 分钟把流量交给陌生出口（实测签到检测中途
  节点被换掉），且单样本抓不住节点分钟级坏相。
- 节点健康检查用中立 204 URL（gstatic），**不再用医院首页**——见 §5 自伤教训。
- 探针每测一次 = 直连（本机）+ 代理（mihomo delay API 经钉住节点）各一发；
  双不通时全量重测医院可达性并钉上最快通过者（即时自愈）。

## 关键运维认知（2026-09-16/17 线上排查定论）

### 1. 502 只能来自代理链路，直连失败永远表现为超时

医院对服务器 IP 的封禁是**静默丢包**，直连失败 = 超时，不产生 HTTP 状态码。
app 所有医院请求统一走 `PROXY_URL`，因此每一个 502 都是代理链路产生的：

- mihomo 日志**有** `dial hospital ... error` 警告 → mihomo 到节点拨号失败
  （自产 502，如组被手动切到 DIRECT 而直连被封时）；
- mihomo 日志**无**拨号警告 → 拨号成功，502 是节点上游（机场中转链路/
  家宽出口）返回后透传的，属节点链路质量问题。

2026-09-17 补充：**空响应体 502 的另一个成因**——Trojan 入口成功拨号、但入口
向后端出口/目标拨号失败时直接关闭流，mihomo 对 HTTP 入站合成空体 502，
日志不留任何错误（debug 级也只见正常 [TCP] 转发记录）。

### 2. 节点失败的真相：DNS 轮询入口 + 分钟级整段坏相

中转节点入口域名（rrr*/tube-cat）DNS 轮询到多台 AWS 中继（每条新连接重新
抽签）；IEPL 节点入口是独立域名（Sclass-*/catcat321 → GCP 单 IP）。
失败不是均匀散布的「每连接抽签」，而是以几十秒～几分钟为单位的**整段坏相**
——坏相窗口内实测 27 连发全 502，同一节点几分钟后又恢复 200。
同秒对齐采样证明 delay 测试与真实流量结果一致——「测速过、流量挂」是
两次采样落在相位边界两侧的采样假象，不是链路差异。

推论：**任何单样本探测都只能代表当下这一秒**；对抗坏相的唯一有效手段是
跨时间重试（签到的 5 分钟重试循环天然免疫坏相）。

对策（已实施）：`HospitalClient._request` 对 5xx/传输错误有限重试
（登录链路与拉列表，签到动作本身靠外层 5 分钟重试循环兜底）；
状态检测改前端逐个串行调用单账号接口、账号间休息 3 秒
（并发在代理环境下放大失败率）。

### 3. 单点操作成功、批量操作全挂 ≠ 网络配置不平行

所有请求同一条代理代码路径。逐请求随机失败率 p 时，单点操作（1–3 个请求）
经常蒙混过关；批量状态检测（9 账号 × 3–4 请求 ≈ 30 次）几乎必踩——
现象上是「只有批量操作挂」，实质是请求数放大了同一失败率。

### 4. 医院侧疑似地域/信用限制，可用节点池远小于订阅规模

全量测速 100 个订阅节点，只有 18 个（港澳台的 16 个 + 2 个假节点）能拿到
医院首页的 200/302；日美欧节点长期全挂。选节点时以实测为准，勿迷信订阅规模。

### 5. 健康检查风暴是自伤来源（2026-09-17 修复）

上线初期（09-16～17）provider 健康检查与 url-test 都以**医院首页**为目标：
98 节点 × 每 5 分钟 ≈ 2.8 万次/天。医院 WAF 视角下这是教科书级扫描器
（近百 IP 轮番 GET 首页），足以成批拉黑机场出口——mihomo 日志中健康检查
时段整批出现的 "forbid" 拦截页即部分出口已被拉黑的证据；机场视角下同账号
全中继反复请求同一冷门站点同样是异常模式。对比：Windows 客户端测速默认打
`gstatic.com/generate_204`，医院永远看不到，机场看到的也是正常客户端。

09-17 起健康检查/测速全部改用中立 204 URL；医院 URL 只出现在 app 低频
实测路径（每小时探针 1 次/通道 + 失败触发的全量重选）。

## 已修复

### v0.2.0（2026-09-16～17：代理逃生通道从部署到可用）

**部署修复**
- `docker-compose.yml`：mihomo 镜像自带 `ENTRYPOINT /mihomo`，compose 的
  `command: sh -c "sed ..."` 不覆盖 ENTRYPOINT，sed 注入从未执行。
  修复：加 `entrypoint: ["sh", "-c"]`，命令改 list 单元素形式。
- `config.template.yaml`：`allow-lan: false` 时 mixed-port 只绑容器内
  127.0.0.1，app 容器经 docker 网络连不上。修复：`allow-lan: true`
  （7890 未映射宿主，仅 docker 内网可达）。

**出口与节点架构（三天试错定稿）**
- **fallback 组反复横跳/不切换**：组类型改 selector，出口决策收归 app 探针
  （fallback 健康检查对 DIRECT 的判定不稳，与 app 逃生切换互相覆盖）。
- **url-test 每 5 分钟换节点**：info 日志实锤真实流量中途被改选（前 4 个
  请求走 IEPL 01、第 5 个起变中转 02）；且手动钉选会被周期测速冲掉、
  死节点钉不上。节点选择改 app 钉选（hospital-pin select 组）：
  实测失败才重选，好节点一直用。
- **节点死亡无自愈兜底**：探针在直连与当前节点双失败时全量重测医院可达性，
  钉上最快通过者，不等周期测速。
- **健康检查风暴**：见 §5，健康检查/测速 URL 改中立 204。
- **502 文案误导**（「代理节点或上游异常」在 DIRECT 被墙时也出现）：
  双通道探针分开报告两通道状态，语义明确。
- **失败探测 channel 恒为 direct**：双不通时记录当前实际出口。
- **节点列表读错接口**：订阅节点不注册在 `/proxies` 命名空间（直查 404
  刷屏），改读 `/providers/proxies` 的 sub 订阅（default/hospital 伪
  provider 含组对象，需排除）。
- **httpx INFO 日志噪音**：降为 WARNING。
- **订阅假节点参与测速**：`exclude-filter` 剔除（剩余流量/套餐到期等）。
- **订阅每天才刷新**：改为每小时（`interval: 3600`）。
- **启动后出口随机**：mihomo 重启后 hospital 默认 DIRECT、pin 组默认订阅
  首节点，app 启动 30 秒后自动补一次探测收敛。

**状态检测**
- **整页 504 + 并发放大失败率**：check-all 把全账号合并在一个请求里
  （限并发 3 + 错峰），代理抖动时总时长顶破网关 60s 超时——浏览器 504
  整页崩掉，已完成的账号也看不到结果（实测 9 账号只落库 3 个）；且代理
  环境下多连接同节点并发等于逐请求抽签，并发越高失败面越大。改为前端逐个
  串行调用 `/admin/check-one/<id>`（单账号短请求），每完成一个立即落库并
  刷新该行徽标，账号间休息 3 秒；单个请求超时/504 只影响一行，循环继续。

## 备注

- `Unsolicited response received on idle HTTP channel starting with "forbid..."`
  日志：改中立 204 测速前，每 5 分钟整批出现于**健康检查**——某些节点出口
  对医院 URL 返回拦截页（出口 IP 已被医院拉黑），迟到字节落在已空闲的
  HTTP 连接上。改中立 204 后此类日志应消失；若仍出现说明出口封锁未愈。
- 镜像拉取：`docker.1ms.run` 对 `metacubex/mihomo` 大层会卡死，部署侧改用
  `dockerproxy.net/metacubex/mihomo:latest` 拉取后 `docker tag` 成本地镜像。
- 启动后第一轮健康检查可能测出 `delay=0` 误报，下一轮（约 5 分钟）自愈。
